# 协议获取过程

简体中文 | [English](REVERSE_ENGINEERING.en.md)

两端 public MAC 已知且协议匹配时，正常部署与日常控制不需要 Nordic 或重新抓包。首次地址未知，或新遥控器／音箱协议存在差异时，可能需要以下研究路径。

音箱在原遥控连接中是 BLE central，不能由 Wi-Fi MAC 或普通广播扫描猜测其身份。地址确认需监听连接建立并核对发起方与地址类型，或取得可靠端点记录；这些身份研究与按键协议解码是不同的步骤。

1. 普通电脑扫描主要看广播。已连接遥控器不一定继续可连接广播，扫描不到不等于没有发射。nRF52840 用于 BLE；不是所有蓝牙制式的通用监听器。
2. Nordic 空口捕获确认了广播与加密连接，但本次没有得到足够的配对/加密启动材料，无法从那些抓包直接恢复全部按键。不能把空口密文当作可重放的控制协议。
3. 将音箱关闭、让遥控器进入配对，改由 Windows 作为合法端点。Windows HCI 完整日志配合隔离按键序列取得报告字节；Windows Raw Input 的按键映射仅为辅助，最初按时间猜测 USB=Esc 的结论已撤销。
4. Nordic connectivity 固件作为独立 GATT 客户端，合法配对并读取 0x2908 Report Reference，确认输入 ID 1/3/30 与对应特征。该路线还捕获了电源键，避免让电源键被电脑解释为系统操作。
5. 将 79 字节 HID Report Map 与 GATT 服务结构复现到 ESP32。ID 3 描述符宣称四字节，但实际输入通知为两字节；实现保留实测长度，不能按标准 HID 名称重新解释按键语义。
6. 原装遥控器和模拟遥控器直接同时连接音箱未形成稳定方案，因此实现 ESP32 的 BLE 客户端+服务端中转。认证、CCCD 订阅、绑定持久化和连接恢复都需要分别处理。

## 文件定位

- `jbl_protocol.json`：协议事实、按键来源及原始帧/行定位。
- `evidence/hid-report-map.bin`：不含凭据的 79 字节描述符。
- `scan_ble.py`：操作系统解码的广播扫描，不是原始无线报文监听。
- `capture_remote.py`：Nordic legacy Sniffer API 研究脚本，需单独安装官方 SDK，必须指定端口及目标；不是部署必需项。
- `inspect_remote.py`：与明确指定的遥控器建立端点连接并读 GATT，会改变当前连接关系，只用于受控研究。
- `inspect_hid.py` / `inspect_hid_caps.py`：Windows HID 端点研究脚本。
- `validate_jbl_protocol.py`：使用本地私有原始抓包交叉验证；缺少原始文件时不能运行完整历史验证。

研究时仅操作自己的设备。临时完整 HCI 日志可能记录其他蓝牙连接及密钥，应限制采集时段并恢复原日志设置。本项目原始研究的临时完整日志已关闭并恢复。
